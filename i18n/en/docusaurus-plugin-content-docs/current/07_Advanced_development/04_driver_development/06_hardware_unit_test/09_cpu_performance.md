# CPU Performance Testing

```mdx-code-block
import DocScope from '@site/src/components/DocScope';
```

## Overview

This test uses the CoreMark benchmark program to evaluate the integer computing performance of the CPU. It records the CoreMark score (`Iterations/Sec`) in single-core and multi-core modes, so that you can compare the effect of optimization level, core count, and operating frequency on computing performance.

The CoreMark source code is pre-installed on the development board in the `/app/chip_base_test/07_cpu_performance/coremark-main/` directory. Compile it as described in [Usage](#usage) before running.

:::tip
Only the CoreMark source code is provided on the board. There are **no** pre-built `coremark_O3_single` or `coremark_O3_multi` executables. Both must be generated by compiling with the commands in this document.
:::

## Test Principles

`CoreMark` is a widely used benchmark program for evaluating CPU performance in embedded systems. Its core testing methodology involves simulating typical computational tasks found in embedded applications to assess CPU performance under common computational patterns. The test is based on the following key elements:

- Algorithm selection: CoreMark employs several fundamental algorithms and operations.
  - Integer operations: including addition, multiplication, bitwise operations, and other common operations.
  - Data structures: the test includes operations on linked lists, queues, and other data structures.
  - Control structures: involving basic control flow constructs such as loops and conditional statements.
  - Matrix multiplication and basic computational tasks: used to simulate common numerical computation workloads.
- Test workloads: the CoreMark workload includes the following aspects.
  - Compute-intensive operations: such as integer addition, multiplication, and bitwise operations.
  - Memory operations: simulating typical memory access patterns, including operations on linked lists and queues.
  - Task scheduling and control: involving complex control flows, such as conditional branching and loops.
- Test environment: CoreMark runs in an environment free from interference by other processes or threads. This ensures that test results are unaffected by OS scheduling, resource management, or other external factors, thereby accurately reflecting the processor's raw computational performance.
- Performance measurement: CoreMark's performance metric is the CoreMark score, which represents the average computational speed of the executed algorithms and tasks during the test. A higher score indicates better processor performance.

## Environment Preparation

- Hardware: one development board with adequate cooling.
- System: an RDK OS image, with access to the board over SSH or the debug UART.
- Dependencies: `gcc` and `make` are pre-installed on the board. No additional packages are required.

Prolonged high-load testing raises the CPU temperature and can trigger thermal throttling, which affects test results. Before testing, make sure of the following:

- The test environment is well ventilated and properly cooled.
- Unnecessary background programs are closed. Use the `top` command to identify and stop non-essential services.
- The board is idle. `top` only shows processes that consume CPU; continuous disk activity (for example, a storage stress test running at the same time) will noticeably depress the score. Use `vmstat 1 3` to confirm that `id` is close to 100 and `wa` is close to 0 before you start.

### Manually Set the CPU Frequency

<DocScope products="RDK S100">

Set the CPU to run in performance mode using the following commands:

```shell
echo userspace >/sys/devices/system/cpu/cpu0/cpufreq/scaling_governor
echo 1500000 >/sys/devices/system/cpu/cpufreq/policy0/scaling_setspeed
```

</DocScope>
<DocScope products="RDK S600">

Set the CPU to run in performance mode using the following command (the maximum frequency of each S600 policy is 2100000kHz):

```shell
echo performance >/sys/devices/system/cpu/cpufreq/policy0/scaling_governor
```

</DocScope>

:::note
In the `cpu frequency` block printed by `hrut_somstatus`, the `cur` column should equal the `max` column, which means the CPU is not throttled. If `cur` is noticeably lower than `max`, switch to performance mode with the command above and confirm adequate cooling before testing.
:::

## Usage

### Compile the Single-Core and Multi-Core Programs

Compile in the `/app/chip_base_test/07_cpu_performance/coremark-main` directory. The commands below compile the program and then automatically run the benchmark once, so the elapsed time includes one full run.

<DocScope products="RDK S100">

The S100 platform features a 6-core Cortex-A78AE; use `-mcpu=cortex-a78` and `-DMULTITHREAD=6`:

Command to compile single-core CoreMark with `-O3` optimization:

```shell
make XCFLAGS="-O3 -funroll-all-loops -static --param max-inline-insns-auto=550 -DPERFORMANCE_RUN=1 -mcpu=cortex-a78" REBUILD=1 run1.log

mv coremark.exe coremark_O3_single
```

Command to compile 6-core CoreMark with `-O3` optimization:

```shell
make  XCFLAGS="-O3 -funroll-all-loops -static --param max-inline-insns-auto=550 -DPERFORMANCE_RUN=1 -mcpu=cortex-a78 -DMULTITHREAD=6 -DUSE_PTHREAD -lrt -pthread" REBUILD=1 run2.log

mv coremark.exe coremark_O3_multi
```

</DocScope>
<DocScope products="RDK S600">

The S600 platform features an 18-core Cortex-A78AE; use `-mcpu=cortex-a78` and `-DMULTITHREAD=18`:

Command to compile single-core CoreMark with `-O3` optimization:

```shell
make XCFLAGS="-O3 -funroll-all-loops -static --param max-inline-insns-auto=550 -DPERFORMANCE_RUN=1 -mcpu=cortex-a78" REBUILD=1 run1.log

mv coremark.exe coremark_O3_single
```

Command to compile 18-core CoreMark with `-O3` optimization:

```shell
make  XCFLAGS="-O3 -funroll-all-loops -static --param max-inline-insns-auto=550 -DPERFORMANCE_RUN=1 -mcpu=cortex-a78 -DMULTITHREAD=18 -DUSE_PTHREAD -lrt -pthread" REBUILD=1 run2.log

mv coremark.exe coremark_O3_multi
```

</DocScope>

:::note
The commands above do not set `PORT_DIR` explicitly. On a Linux board the `linux` port is selected automatically. That port sets `PORT_CFLAGS` to `-O2`, so both `-O2` and the `-O3` from `XCFLAGS` appear in the printed `Compiler flags` line (as `-O2 -O3 ...`). GCC honours the last `-O` option (`PORT_CFLAGS` precedes `XCFLAGS`), so the effective level is still `-O3`; the extra `-O2` does not change the benchmark result.
:::

### Multi-Core Thread Count

The number of parallel threads in the multi-core test is fixed at **compile time** by `-DMULTITHREAD=N`. The executable itself provides no thread-count option such as `-c`. When you run `./coremark_O3_multi -c<N>`, `-c<N>` is not recognized as a thread-count argument and the program still runs with the compiled-in thread count. A board measurement confirms this: the output is identical to running without arguments. Running `./coremark_O3_multi` on its own is therefore sufficient.

To reduce the number of parallel threads at run time (never above the compiled-in `MULTITHREAD` value), pass `M<threads>` as the first argument. A board measurement of `./coremark_O3_multi M4` prints `Parallel PThreads : 4`.

## Running Result

### Success Indicators

A successful run ends with the following output:

- `Correct operation validated. See README.md for run and reporting rules.`
- No `Errors detected` line.
- A `CoreMark 1.0 : <score> / ...` line. This line is printed only for a `2K performance run`; `<score>` is the `Iterations/Sec` value used for scoring.

For a `2K performance run` (where `seedcrc` is `0xe9f5`), the algorithm check values of every thread should be:

| Field | Expected value |
|---|---|
| `[N]crclist` | `0xe714` |
| `[N]crcmatrix` | `0x1fd7` |
| `[N]crcstate` | `0x8e3a` |

:::note
`[N]crcfinal` is not a validity indicator. It is derived from the number of iterations actually executed, and by default (`ITERATIONS=0`) CoreMark **calibrates `Iterations` by trial runs** at startup: it ramps up through 10, 100, 1000... until a single run exceeds 1 second, then scales the count so the measured run takes about 10 seconds. Platforms with different single-core speeds therefore end up with different `Iterations`, and `crcfinal` differs accordingly; on the same platform the single-core and multi-core runs use the same per-thread iteration count and produce the same `crcfinal`. CoreMark validates only `crclist`, `crcmatrix`, and `crcstate`.

During a multi-core run, every thread prints its own set of `[N]crc*` lines. The two multi-core outputs above keep only the `[0]` set and elide the rest with `...`; each thread's values are identical to `[0]`.
:::

### Result Parameter Explanation

- **`CoreMark Size`**: Indicates the code and data size of the CoreMark benchmark, measured in bytes.
- **`Total ticks`**: Represents the total number of CPU clock cycles consumed during the test.
- **`Total time (secs)`**: The total duration of the test, in seconds. A result is valid only if this value is at least 10 seconds.
- **`Iterations/Sec`**: The number of iterations executed per second, which is the `CoreMark` score in the scoring formula.
- **`Iterations`**: The total number of iterations executed throughout the entire test.
- **`Parallel PThreads`**: The number of parallel threads actually used by the multi-core test, equal to the compile-time `-DMULTITHREAD` value (it can be lowered at run time with the `M<n>` argument).
- **`seedcrc`**: The seed checksum, used to identify the run profile. `0xe9f5` corresponds to a `2K performance run`.
- **`Compiler flags`**: Compiler options used during compilation.
- **`CoreMark 1.0`**: A summary of key information. The value is the CoreMark performance score, representing iterations per second. A higher value indicates stronger processor performance.

:::note
Repeated runs on the same board in the same idle state typically vary within 5% in `Iterations/Sec`. When comparing results across optimization levels or core counts, take the average of several runs under the same cooling conditions and at the same frequency. Background load on the board (especially disk activity) depresses the score noticeably, so results obtained under different states should not be compared with each other.
:::

## Test Metrics

The following metrics should be measured under an idle system and averaged over multiple runs. The standard CoreMark scoring formula is:

<img src="https://rdk-doc.oss-cn-beijing.aliyuncs.com/doc/images_to_upload/coremark_formula.png" alt="Test Metrics diagram" style={{ width: '100%', maxWidth: '980px', height: 'auto', display: 'block', margin: '0 auto' }} />

- `CoreMark Iterations/Sec`: The number of CoreMark benchmark iterations executed per second, typically reflecting processor performance. Higher iteration counts indicate greater computational capability.
- `CPU Clock (MHz)`: The processor's clock frequency, measured in MHz (megahertz). It reflects the processor's operating speed.
- `CPU Cores`: The number of processor cores. CoreMark can be tested in either single-core or multi-core mode.

### Scoring Criteria

- CoreMark with `-O3` optimization: the single-core score should reach X > 4.2.
- CoreMark with `-O2` optimization: the single-core score should reach X > 4.2.

<DocScope products="RDK S100">

The S100 platform features a 6-core Cortex-A78AE (CPU Clock = 1500MHz). Board-measured:

Based on the single-core test result under `-O3` optimization: CoreMark Iterations/Sec = 15529 iterations/second, CPU Clock (MHz) = 1500MHz, CPU Cores = 1 (single-core test). The score is calculated as `CoreMark Score = 15529 / (1500 x 1) = 10.35`, which is well above the typical `-O3` baseline (4.2) and represents excellent performance.

Based on the multi-core test result under `-O3` optimization: CoreMark Iterations/Sec = 90538 iterations/second, CPU Clock (MHz) = 1500MHz, CPU Cores = 6 (multi-core test). The score is calculated as `CoreMark Score = 90538 / (1500 x 6) = 10.06`, which also far surpasses the `-O3` multi-core baseline (4.2), indicating strong overall system computational capability.

### Understanding the Scoring Criteria

These two scoring criteria (for `-O3` and `-O2`) establish minimum performance requirements for the processor under different optimization levels. The significance of these scores is as follows:

- `-O3` optimization represents the highest optimization level in GCC and other compilers, employing aggressive optimization strategies to maximize execution speed. This level enables numerous performance-enhancing features such as loop unrolling and function inlining, aiming for peak computational performance.
- `-O2` optimization is a more conservative level. Compared to `-O3`, `-O2` avoids certain aggressive optimizations that might increase code size. Thus, `-O2` typically delivers a more balanced performance, maintaining both efficiency and portability.

## FAQ

### Error: Must execute for at least 10 secs for a valid result

**Cause**: The run lasted less than 10 seconds, so the result is invalid.

**Solution**: Do not set an excessively small `ITERATIONS`; use the default automatic mode (`ITERATIONS=0`).

### Error: list crc / crcmatrix / crcstate - should be ..., followed by Errors detected

**Cause**: Algorithm check values do not match and the result is unreliable.

**Solution**: Confirm the compile options match this document, confirm no other process is competing for the CPU, then rebuild and retry.

### Error: Cannot validate operation for these seed values

**Cause**: The seed combination passed in does not belong to any known profile.

**Solution**: Run `./coremark_O3_single` or `./coremark_O3_multi` without positional arguments, as shown in this document.

### Iterations/Sec is noticeably lower than expected

**Cause**: The CPU is being throttled, or background load is present.

**Solution**: Use `hrut_somstatus` to confirm that `cur` equals `max` in the `cpu frequency` block, and switch to performance mode if needed; also use `vmstat 1 3` to confirm that `wa` is close to 0, ruling out background load such as disk activity.

### Parallel PThreads in the multi-core output is not the expected core count

**Cause**: The thread count is determined at compile time by `-DMULTITHREAD`; the executable itself provides no thread-count option.

**Solution**: Recompile for the target core count instead of relying on a run-time argument.
